# Server on Effect v4 rc, pinned exactly; SQLite through effect/sql; SSE with replay; a types-only Client

The server is TypeScript on Node 24, because the Pi SDK is TypeScript and runs in-process (ADR-0001). It is built on Effect v4 (`effect` plus `@effect/platform-node`), pinned exactly to `4.0.0-rc.118`. The whole `@effect/*` family is held to that version with pnpm overrides, because the v4 release candidates break their APIs from week to week and the packages depend on each other through caret ranges. We chose v4 over the stable v3 because v4's single `effect` package already holds what convo needs: `HttpApi` for the Client-facing API, `HttpStaticServer` in SPA mode for serving the Client, and `effect/sql` with `SqlSchema` and `SqliteMigrator`. Starting on v3 would mean migrating to v4 soon afterwards. Storage is SQLite through `@effect/sql-sqlite-node`, which runs on Node's built-in `node:sqlite`, so there is no native addon to build. We write SQL by hand behind a repository service and use no ORM. We considered Drizzle and rejected it: it would add a second schema language alongside Effect Schema and its own database layer beside `effect/sql`. Live Session transcripts and Task updates go to the Client as Server-Sent Events. Each event carries its sequence number as the SSE `id`, so a reconnecting `EventSource` resumes from `Last-Event-ID`, and the server replays the stored events it missed. SSE fits because the stream only flows from server to Client and the browser reconnects on its own. The web Client imports only *types* from the `api` package, never Effect at runtime, so Effect's rc churn stays out of the browser bundle; a Vite plugin fails the build on any runtime import of `effect`, `@effect/*` or `@convo/api`. TypeScript is pinned to 6.0, the newest line `@effect/language-service` supports (TypeScript 7 would need `@effect/tsgo` instead). The costs: we track a moving rc by hand, and the Client re-declares its fetch calls instead of using a generated Effect client.
